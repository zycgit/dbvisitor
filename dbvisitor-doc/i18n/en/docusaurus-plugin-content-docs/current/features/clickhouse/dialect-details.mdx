# ClickHouse Dialect Details

## Pagination SQL

The ClickHouse dialect uses `LIMIT offset, count`; offset=0 produces only `LIMIT count`:

```sql
SELECT ... LIMIT ?, ?
```

## Count SQL

```sql
SELECT COUNT(*) FROM (original query) as TEMP_T
```

## Identifier Quoting

The dialect uses backticks:

```sql
SELECT * FROM `users` WHERE `name` = ?
```

## Write Conflict Strategies

ClickHouse **does not support** Ignore / Update conflict strategies:

| Strategy | Supported | Notes |
|------|:------:|------|
| Into | ✓ | Regular INSERT |
| Ignore | ✗ | Not supported |
| Update | ✗ | Not supported |

ClickHouse is an analytical database; there is no traditional OLTP primary key conflict concept.

## Generated Key Strategy

| Scenario | GeneratedKeyStrategy |
|------|---------------------|
| No backfill columns | `JdbcBatch` |
| With backfill columns | `OneByOne` |

**Relying on JDBC generated keys is not recommended**. ClickHouse does not use the database auto-increment primary key model; business identifiers should be generated application-side (UUID, Snowflake ID, etc.).

## Sequences

Not supported. ClickHouse does not implement `SeqSqlDialect`.

## Write Recommendations

- ClickHouse recommends batch writes over row-by-row inserts
- `JdbcBatch` can be used for throughput when no backfill is needed
- Visibility depends on the table engine and settings. With async_insert enabled and wait_for_async_insert disabled, acknowledgement can precede insertion into the table; this is not the default behavior of every INSERT. See [asynchronous inserts](https://clickhouse.com/docs/optimize/asynchronous-inserts)
- Recommended primary key generation: `KeyType.UUID32` or `KeyType.UUID36`

## Key Differences Summary

- The dialect provides Into writes, not Ignore/Update conflict strategies
- Relying on JDBC generated keys is not recommended
- Sequences not supported
- Analytical write model; usually submit multiple rows together
