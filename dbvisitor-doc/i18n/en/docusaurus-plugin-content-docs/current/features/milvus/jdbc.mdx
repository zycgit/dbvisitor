Install and configure the [independent JDBC driver](../../drivers/milvus/connection.mdx) first. These examples use JDBC directly and do not require dbVisitor's upper-level APIs. Unless the example opens its own connection, `conn` denotes an open JDBC connection owned and closed by the application.

## Complete Getting-Started Example {#2-complete-getting-started-example}

Prerequisites: Milvus is running, the `default` database is accessible, and your user can create collections/indexes, load, read and write. The example creates a new `books_demo` collection with a two-dimensional FloatVector and an L2 index.

Save as `MilvusJdbcExample.java` and run in a Java project with the [driver dependency](../../drivers/milvus/connection.mdx). It connects locally by default; pass a JDBC URL as the first program argument to override it. Before rerunning, choose a different collection name or clean up the demonstration collection yourself. The example does not automatically delete existing data.

```java
import java.sql.*;
import java.util.Properties;

public class MilvusJdbcExample {
    public static void main(String[] args) throws Exception {
        String url = args.length == 0
                ? "jdbc:dbvisitor:milvus://127.0.0.1:19530/default"
                : args[0];
        Properties props = new Properties();
        props.setProperty("consistencyLevel", "Strong");
        props.setProperty("connectTimeout", "10000");
        props.setProperty("maxRetry", "3");
        // If authentication is enabled:
        // props.setProperty("token", "YOUR_TOKEN");

        Class.forName("net.hasor.dbvisitor.driver.JdbcDriver");
        try (Connection conn = DriverManager.getConnection(url, props)) {
            try (Statement stmt = conn.createStatement()) {
                stmt.executeUpdate("CREATE TABLE books_demo (" +
                        "book_id INT64 PRIMARY KEY, title VARCHAR(200), " +
                        "word_count INT32 DEFAULT 0, book_intro FLOAT_VECTOR(2))");
                stmt.executeUpdate("CREATE INDEX idx_intro ON books_demo (book_intro) " +
                        "USING 'FLAT' WITH (metric_type='L2')");
                stmt.executeUpdate("LOAD TABLE books_demo");
            }

            String insert = "INSERT INTO books_demo " +
                    "(book_id, title, word_count, book_intro) VALUES (?, ?, ?, ?)";
            try (PreparedStatement ps = conn.prepareStatement(insert)) {
                ps.setLong(1, 1L);
                ps.setString(2, "A book");
                ps.setInt(3, 1000);
                ps.setObject(4, new float[] {0.1F, 0.2F});
                System.out.println("inserted=" + ps.executeUpdate());
            }

            String search = "SELECT book_id, title, score FROM books_demo " +
                    "WHERE word_count >= ? ORDER BY book_intro <-> ? LIMIT ?";
            try (PreparedStatement ps = conn.prepareStatement(search)) {
                ps.setInt(1, 100);
                ps.setObject(2, new float[] {0.1F, 0.2F});
                ps.setInt(3, 5);
                ps.setFetchSize(128);
                ps.setQueryTimeout(30);
                try (ResultSet rs = ps.executeQuery()) {
                    while (rs.next()) {
                        System.out.printf("%d %s %.4f%n", rs.getLong("book_id"),
                                rs.getString("title"), rs.getFloat("score"));
                    }
                }
            }
        }
    }
}
```

`score` is the distance/similarity result column, not a stored field. Smaller L2 scores are nearer. `Class.forName` explicitly registers the driver; normal classpath environments can also use JDBC service discovery.

For authentication, TLS/mTLS, Zilliz Cloud and all connection properties, see [Connection Parameters](../../drivers/milvus/params.md). See [Versions and Support](./compatibility.md) for server and feature requirements.

### Connection Pools and Session {#pool-session}

Pass a Milvus JDBC DataSource to dbVisitor's `Configuration.newSession(dataSource)`, `newJdbc(dataSource)`, or `newLambda(dataSource)`. A Session can create BaseMappers, and multiple entity types or Sessions can share one configuration. This does not make operations transactional.

With HikariCP, explicitly set `connectionTestQuery` to `SHOW TABLES`: the current shared driver does not implement `Connection.isValid()`. Do not use the unsupported `SELECT 1`. Keep auto-commit enabled and do not configure a transaction isolation level. Configure the URL, authentication, and TLS as for a normal JDBC connection, and close the pool when the application exits.

Entities must match the collection schema. Milvus requires a single primary-key field, not a composite key. Required vectors must be supplied by the application or generated by a native function already defined in the collection. Session does not invent missing field values or turn VARCHAR date text into native date types.

A Session can mix annotation mappers and XML RefMappers created by `createMapper` with `createBaseMapper`. After registering XML or mapper interfaces through `Configuration.loadMapper`, use `session.executeStatement("namespace.statementId", params)` for DML and `queryStatement` for mapped result lists; BaseMapper exposes the same statement-forwarding methods. SQL must remain within Milvus syntax: successful registration does not make JOIN, scalar ORDER BY or relational functions executable. Repeating a simple primary-key deletion may still return 1; do not infer prior entity existence from that count. See [return-count boundaries](./commands.md#jdbc-results).

### Entity and Collection Mapping {#entity-mapping}

Use dbVisitor annotations, XML, or `MappingRegistry` to map entity properties to collection fields. To use an entity with another existing collection, call `configuration.getMappingRegistry().loadEntityAsTable(Entity.class, "target_collection")` before creating its BaseMapper, then create the Session and BaseMapper from that same `Configuration`. Take the target collection name from trusted configuration, and ensure the entity fields and single-field primary key match the target schema.

This registers an entity mapping; it does not create or rename a collection. Do not register the same entity twice in one configuration. Namespaces, field aliases, and type handlers are configuration metadata: being able to describe an index, dialect, or DDL strategy in a mapping does not mean Milvus can execute it. Manage collection schemas, indexes, and native functions through the [Milvus commands](./commands.md).

### Field Type Handlers {#field-type-handlers}

Field mapping supports `@Column` renaming, insert/update exclusion policies, read-only fields, `@Ignore`, and explicit column mapping. Entity-mapped Map queries use property names as keys and ignore unmapped result columns, so a collection can retain unmapped vector fields. This differs from a JdbcTemplate Map query that reads all returned columns. Explicit NULL writes require nullable target fields; mappings do not change the collection schema.

Use `@Column(typeHandler=YourTypeHandler.class)` to select a custom field handler, `jdbcType=Types.VARCHAR` / `Types.INTEGER` to specify JDBC binding types, or `specialJavaType=String.class` to supply a concrete mapping type for a declaration such as `CharSequence`. Unspecified fields continue to use dbVisitor's default handlers.

Handlers participate in parameter binding and result mapping; they do not change Milvus collection field types. Converted values must match the schema. For example, uppercasing a string in a handler is application-side processing, not a Milvus SQL function. A `jdbcType` declaration does not add server support for native DATE, arbitrary objects, or other unsupported types.

### Scalar type boundaries {#scalar-types}

Java Byte/Short/Integer/Long map to INT8/INT16/INT32/INT64, Float/Double to FLOAT/DOUBLE, Boolean to BOOL, and strings or single characters to VARCHAR. Nullable fields can store NULL; an empty VARCHAR string differs from NULL, and Unicode text is subject to the max_length byte limit.

Map BigInteger only to values within the Int64 range. Writing BigDecimal to DOUBLE converts it to double-precision floating point and may lose precision; reading the result as BigDecimal does not provide native DECIMAL or arbitrary-precision arithmetic. Applications requiring exact decimals must explicitly design their storage representation; the driver does not simulate DECIMAL. Milvus 2.6.2 does not provide relational BIT/CAST semantics, and BOOL is not a substitute.

### Enum mapping {#enum-mapping}

dbVisitor type handlers convert enums to native Milvus scalar values; no native ENUM field is required:

- A plain Java enum uses its constant name in VARCHAR, such as `ACTIVE`.
- An enum implementing `net.hasor.dbvisitor.types.handler.string.EnumOfCode` uses the string returned by `codeName()` in VARCHAR.
- An enum implementing `net.hasor.dbvisitor.types.handler.string.EnumOfValue` uses the integer returned by `codeValue()` in INT32, not an implicit `ordinal()`.

JdbcTemplate parameter arrays can contain these enum objects for INSERT, UPDATE and WHERE value binding. Pass the enum class to queryForObject when reading, for example `jdbcTemplate.queryForObject("SELECT status FROM docs WHERE id=?", new Object[] { id }, Status.class)`. The status field type and stored values must match Status's mapping convention.

NULL in a nullable scalar column maps to null. Unknown names fail for plain enums; unknown custom codes follow the valueOfCode implementation, which may return null or throw. This verifies dbVisitor/JdbcTemplate conversion, not arbitrary enum support in raw JDBC PreparedStatement.setObject. It does not supply a collection's required vector fields.

### Map-based access {#map-access}

Milvus collections can be accessed through dbVisitor's mapped Map, freedom Map and BaseMapper Map methods. Their keys have different meanings:

| Mode | Entry-point examples | Map keys |
| --- | --- | --- |
| Mapped Map | `lambda.insert(UserInfo.class).asMap().applyMap(values)`; `lambda.query(UserInfo.class).asMap()` | Entity property names, such as `createTime`, translated through mappings to collection fields such as `create_time` |
| Freedom Map | `lambda.insertFreedom("user_info").applyMap(values)`; `lambda.queryFreedom("user_info")` | Collection field names such as `create_time`, without an entity class |
| BaseMapper Map | `mapper.updateByMap(values)`, `mapper.replaceByMap(values)`, `mapper.deleteByMap(keys)` | Registered entity property names; primary-key properties supply update/delete conditions |

`lambda` is a LambdaTemplate created with the Milvus DataSource, and `mapper` is the entity's BaseMapper. Execute insert builders with `executeSumResult()`; use queries such as `eq("id", id).queryForMap()` or `queryForObject()` for one Map, and finish conditional update/delete builders with `doUpdate()` / `doDelete()`. Collections and entity mappings must already exist; for example, `UserInfo.createTime` must map to the actual `create_time` field. Maps do not bypass schema constraints: required vectors must be supplied or generated by native functions.

BaseMapper `updateByMap` ignores NULL values and absent properties, making it suitable for partial updates. In contrast, `replaceByMap` replaces writable non-key fields in the entity mapping: explicitly NULL and omitted properties may both be written as NULL. Supply every field you intend to retain, and ensure cleared fields are nullable. `upsertByMap` retains dbVisitor's query-then-insert-or-replace-update flow; it is not a direct alias for driver SQL UPSERT and does not make the existence check and write atomic. `deleteListByMap` combines multiple primary-key Maps into delete conditions; it is not JDBC addBatch/executeBatch and provides no transaction rollback guarantee.

Use application-defined or allowlisted table names, column names and Map keys; supply external input only as condition and write values. Freedom Map does not extend Milvus SQL capabilities. Do not put subqueries, ordering expressions or other SQL fragments into field names, and do not treat rejection of one malformed input as proof that arbitrary SQL concatenation is safe.

### Mapper Parameters and Results {#xml-results}

Entity naming supports camel-case to underscore mapping, `@Column` overrides, and method-reference resolution. Collection names retain their case, and differently cased collections can be accessed separately. Freedom Map's `caseInsensitive` option controls lookup of returned keys; it does not change server field names or SQL case. The current Milvus dialect has no identifier qualifiers: `useDelimited` does not provide backtick/double-quote identifiers or automatic keyword escaping. Prefer ordinary letters, digits, and underscores in names.

Annotation Mappers propagate SQL parsing errors and execution errors such as missing collections or fields. Queries through an existing Mapper also fail after the collection is dropped. INSERT does not reject duplicate primary keys, and primary-key DELETE acknowledgements do not guarantee the number of existing entities. Do not assume relational duplicate-key exceptions or zero counts for unmatched deletes.

XML Mappers support `statementType="PREPARED"` for bound values or `STATEMENT` for SQL without bound parameters, combined with `fetchSize`, `timeout`, and `resultSetType="FORWARD_ONLY"`. STATEMENT does not turn text substitution into safe value binding; the driver rejects scrollable result-set types.

XML `<where>/<if>/<choose>/<when>/<otherwise>/<foreach>` can combine native scalar predicates with vector ordering; `<set>/<if>` can generate partial UPDATE statements. `@{and}` and `@{in}` rules also work, but the resulting SQL must follow Milvus syntax. Keep mandatory authorization or business scope in unconditional predicates, not optional branches; do not use `WHERE 1=1` as a general Milvus condition prefix. Dynamic tags control SQL generation, not transactions or unsupported server expressions.

Annotation Mapper can bind properties of a single Bean, named `@Param` values, or positional `?` parameters. Multi-parameter methods bind only parameters referenced by SQL. `@{in, :ages}` expands an array or List into placeholders while keeping elements bound as values. Date parameters are mapped to VARCHAR by type handlers, not native server-side date operations; use explicit date parameters instead of a relational `CURRENT_TIMESTAMP` macro in Milvus INSERT.

XML Mapper supports entity, Map, or scalar `resultType`, named `resultMap`, `resultRowMapper`, and `resultSetExtractor` for Milvus SELECT. `ColumnMapRowMapper`, `ColumnMapResultSetExtractor`, and `PairsResultSetExtractor` process columns returned by the driver. Pairs requires a key/value two-column projection, and its Map is one element of the list returned by Session.queryStatement. `<sql>/<include>` can reuse native query fragments without extending SQL syntax. Result types and handlers do not make unsupported scalar ORDER BY, JOIN, or other syntax available.

Annotation Mappers also support `@Query(resultRowMapper=...)` and `resultSetExtractor=...`, combined with fetchSize and timeout. The same handler processes successive pages, with RowMapper row numbers increasing continuously from 0. SQL must still use native syntax; scrollable ResultSets are unsupported.

Ordinary annotated queries can map full or partial entities, single-row and list Maps, and single-column scalars (including COUNT and date fields). When no row matches, single-object queries return null and list queries return an empty list; nullable fields preserve null. Return types do not extend server syntax: changing a Mapper return type does not enable queries containing DISTINCT, MAX/GROUP BY, scalar ordering, or LIKE parameter templates unsupported by the current server version.

### Lambda Conditions and Projections {#lambda-query}

Lambda insertion with `onDuplicateStrategy(DuplicateKeyStrategy.Update)` uses [native partial upsert](./commands.md#upsert), requiring a single mapped primary key whose value is supplied in this write. New keys are inserted; existing keys update only supplied fields, preserving fields omitted by mapping rules. Into/default remains INSERT without duplicate-key rejection guarantees. Ignore has no equivalent native guarantee and is explicitly unsupported, without silently falling back to INSERT or emulating it with read-before-write. Inserts and generated keys use one-by-one execution, not JDBC batch.

Predicates also accept string property names, such as `in("age", values)`, `notIn("age", values)`, `isNull("email")`, `isNotNull("email")`, `between("age", 20, 30)`, and `notBetween("age", 20, 30)`. `eqBySampleMap` generates equality conditions using entity property mappings. These names are Java properties, not arbitrary SQL fragments. Do not assume relational NOT IN three-valued logic when a collection contains NULL elements.

Lambda supports multi-row insertion with `applyEntity(List)`, multi-field updates (including NULL) with `in` predicates, and queries or deletes with `notIn`. `updateTo(false, ...)` leaves that field unchanged. For chunked deletion, repeatedly select one page of primary keys using a range predicate and `initPage(pageSize, 0)`, then delete those keys with IN; read the first page again after each deletion instead of increasing offset. This requires no scalar ordering and provides neither transactions nor a concurrent snapshot. Callers should check progress and bound the operation's scope.

Lambda rejects UPDATE/DELETE without WHERE by default; only an explicit `allowEmptyWhere()` disables this guard. Once allowed, UPDATE can update all records and DELETE can delete all records. For scalar DELETE without WHERE, the driver generates a `primary_key IS NOT NULL` filter from the actual primary-key field, without requiring a handwritten `1=1`; supplied WHERE conditions are never replaced. Direct JDBC/native-command writes without WHERE do not have Lambda's guard, so confirm their scope yourself. An unmatched UPDATE returns 0; the count for simple primary-key DELETE acknowledges submitted keys and cannot establish whether those entities previously existed.

Process native query results through Lambda Map/scalar conversion, RowMapper, RowCallbackHandler, ResultSetExtractor, Pairs, or FilterResultSetExtractor. Use vector ordering with a matching index when stable order is required. Conversion, filtering, or aggregation inside a handler occurs on the client; it does not add server projection expressions, scalar ordering, or GROUP BY. Empty queries do not invoke row handlers.

`iteratorByBatch(batchSize)` and `iteratorForLimit(limit, batchSize, transform)` support paged iteration, result transformation, and empty results; a negative limit traverses all results. Use explicit vector ordering and a matching index when a defined order is needed. Lambda issues separate LIMIT/OFFSET queries and releases each page's JDBC result set after reading it; it does not retain one server-side snapshot. Concurrent changes can affect cross-page consistency. batchSize does not mean JDBC Batch and does not establish high-throughput performance.

Use `orderByL2`, `orderByCosine`, `orderByIP`, or `orderByMetric` for vector ordering and `initPage(k, 0)` for Top-K. Range filters use `vectorByL2`, `vectorByCosine`, or `vectorByIP` and can be combined with scalar predicates such as `eq` through AND. Thresholds follow native Milvus semantics: L2 is squared Euclidean distance below the threshold; COSINE/IP are similarities above it, not PostgreSQL cosine distance or negative inner product. The field index metric must match the query; changing query operators does not give one field multiple index metrics. Do not combine a vector range filter with vector ORDER BY.

Create a LambdaTemplate with `configuration.newLambda(dataSource)`, combine conditions using `eq`, `in`, `and`, `or`, `nested`, and `ifTrue`, and select entity properties with `select`. A single column can be returned as scalars using `queryForList(String.class)`; multiple columns can map to a Map or DTO. Disabled dynamic conditions are omitted from SQL. Use `apply` only for trusted SQL fragments and keep external values in `?` parameters.

Generated SQL has the same Milvus limits: DISTINCT, GROUP BY, SUM/MAX, and scalar ORDER BY are not emulated on the client. Server 2.6.2 rejects `LIKE ?`; native SDK integer template comparisons wrapped in NOT can also trigger a server assertion, including double NOT. The driver does not interpolate parameters or eliminate NOT as a fallback. Ordinary `ne` / `<>` / `!=` comparisons, literal NOT, and `NOT (field IS NULL)` are outside this template issue.

When no rows match, `queryForList()` and `queryForMapList()` return non-null empty lists, and `queryForCount()` returns 0. An empty page created with `usePage(PageObject.of(1, 10))` has zero total rows and zero total pages. In the Lambda API, `initPage(0, 0)` disables pagination; it is not equivalent to SQL `LIMIT 0`.

A nullable VARCHAR field without a default distinguishes an empty string from NULL: query them with `eq(UserInfo::getName, "")` and `isNull(UserInfo::getName)`, respectively. Required vectors must still be supplied or generated by native functions; do not make a nullable business field mandatory merely to generate vectors. An empty string does not bypass the 2.6.2 parameterized LIKE limitation, and an empty result does not make DISTINCT or aggregation supported.

Bind condition values containing quotes, semicolons, or SQL keywords through `eq`, `eqBySample`, or `apply("name = ?", value)`, including text read back from the database and used in another query. Binding protects values, not the SQL fragment passed to `apply`. Server 2.6.2 rejects field predicates combined with constant conditions, such as `.in(UserInfo::getId, ids).apply("1=1")`. The driver propagates that error without removing the condition and retrying, and does not continue with later DELETE statements in the same SQL sequence. Use conditional builders such as `ifTrue` for optional predicates instead of appending constant-true expressions; see [native limits](./compatibility.md#boundaries).

## Common Reads and Writes {#3-common-reads-and-writes}

In these fragments, `conn` is an open JDBC Connection and `books_demo` is the collection created above.

### UPSERT, UPDATE and DELETE

```java
try (PreparedStatement ps = conn.prepareStatement(
        "UPSERT INTO books_demo (book_id, title, word_count, book_intro) VALUES (?, ?, ?, ?)")) {
    ps.setLong(1, 1L);
    ps.setString(2, "Revised book");
    ps.setInt(3, 1200);
    ps.setObject(4, new double[] {0.1, 0.2});
    ps.executeUpdate();
}
try (PreparedStatement ps = conn.prepareStatement(
        "UPDATE books_demo SET word_count = ? WHERE book_id = ? LIMIT ?")) {
    ps.setInt(1, 1500);
    ps.setLong(2, 1L);
    ps.setInt(3, 1);
    ps.setFetchSize(128);
    System.out.println(ps.executeLargeUpdate());
}
try (PreparedStatement ps = conn.prepareStatement(
        "DELETE FROM books_demo WHERE book_id = ? LIMIT ?")) {
    ps.setLong(1, 1L);
    ps.setInt(2, 1);
    System.out.println(ps.executeLargeUpdate());
}
```

UPSERT performs ordinary entity insertion/replacement; provide the necessary entity fields. UPDATE selects primary keys page by page and submits only the primary key plus SET fields, without rewriting other fields. Primary keys cannot be updated. Pages do not provide transactions, whole-operation rollback or exactly-once execution.

INSERT/UPSERT supports multiple VALUES tuples or VALUES ? bound to an Iterable/Iterator, grouped using fetchSize. Counts reflect SDK acknowledgements. Request Statement.RETURN_GENERATED_KEYS and read getGeneratedKeys() for returned keys; JDBC addBatch/executeBatch remains unsupported.

### On-Demand Page Reads

```java
try (PreparedStatement ps = conn.prepareStatement(
        "SELECT book_id, title FROM books_demo WHERE word_count >= ?")) {
    ps.setInt(1, 100);
    ps.setFetchSize(256);
    ps.setMaxRows(1000);
    ps.setQueryTimeout(30);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            System.out.println(rs.getLong("book_id") + ": " + rs.getString("title"));
        }
    }
}
```

This SQL has no LIMIT. maxRows limits returned rows to 1000 and fetchSize controls pages of at most 256. Removing setMaxRows keeps reading matching data without a fixed fallback total cap. Large results, unlimited queries and queries with OFFSET use official iterators. Bounded, single-page queries without OFFSET retain a single Query/Search request.

execute establishes the query and the SDK may prefetch initial data. The driver subsequently pulls pages as JDBC advances and retains only the current page. The limit, EOF, result close, Statement reexecution/close, or Connection close releases the iterator. Later errors may arise from `ResultSet.next()`; always close partially consumed results too.

### Parameter Types {#parameter-types}

- FloatVector: bind a numeric List or a one-dimensional `byte[]/short[]/int[]/long[]/float[]/double[]` using `setObject`. Values are converted to Float and may lose precision. Each distance expression accepts only one query vector.
- `byte[]` means signed numeric elements here, not BinaryVector. boolean[], char[], boxed arrays and multidimensional arrays are not supported FloatVector representations.
- Bind scalar strings with `setString` or `setObject`, including explicit `Types.VARCHAR` / `JDBCType.VARCHAR`. WHERE placeholders become Milvus templates with values sent separately through SDK `filterTemplateValues`, never concatenated into the filter. Do not concatenate user input yourself.
- VARCHAR temporal text: `setDate`, `setTime`, and `setTimestamp` without Calendar use JDBC date/time strings; Timestamp preserves fractional seconds. `setObject(java.util.Date)` uses millisecond-precision Timestamp text. Read with the corresponding `getDate`, `getTime`, or `getTimestamp`; filter parameters use the same text. These are not native DATE/TIMESTAMP types and do not establish support for time zones, Calendar overloads, or server-side date arithmetic. Existing locale-formatted text is not migrated automatically.
- Comparisons, LIKE, IN and function arguments use the same binding. `IN ?` accepts Lists, Java arrays and JDBC Arrays; `IN (?, 'fixed', ?)` binds one array template. Elements must satisfy the SDK's homogeneous-type rules. Byte/Short become Long, Float/BigDecimal become Double (potentially losing precision), and BigInteger must fit Int64. Quotes, backslashes, wildcards and question marks remain data; LIKE wildcards still retain their matching semantics.
- SDK filter templates do not support null; use `IS NULL` / `IS NOT NULL` in WHERE. Non-finite numbers and unsupported objects fail with SQLException, without falling back to expression concatenation. Null values in INSERT/UPSERT/UPDATE SET still follow the field schema.
- Version boundary: Milvus 2.6.2 rejects template parameters on the right of LIKE; integer template comparisons wrapped in NOT also have the native assertion issue described above. The driver does not interpolate parameters or rewrite queries to bypass these failures. Ordinary comparison and IN bindings work; fixed SQL LIKE literals are unaffected by the LIKE template restriction.
- Schema distinguishes JSON from vectors. INSERT/UPSERT JSON fields accept JSON strings, Maps, Lists or JsonElements. See the [syntax manual](./commands.md) for other statement/type boundaries.

Binding follows the [official filter templating mechanism](https://milvus.io/docs/v2.6.x/filtering-templating.md). Query vectors, write entities, LIMIT/OFFSET and search options use their own structured SDK fields, not filter templates. Collection names, field names and operators remain part of the SQL structure.

### Hints and Search Parameters

Hints belong at the start of each SQL command. Only the listed commands consume these settings; unknown hints are not general SDK options.

| Hint | Applicable commands and behavior |
| --- | --- |
| `overwrite_find_limit` | SELECT; positive integer overriding SQL LIMIT. Positive maxRows further caps results. |
| `overwrite_find_skip` | SELECT; nonnegative integer overriding OFFSET. |
| `overwrite_find_as_count` | SELECT; switches to COUNT based on presence, even when set to false. Remove the hint to disable it. |
| `sync` | IMPORT/LOAD/RELEASE; default true, false skips waiting for completion. |
| `timeout` | IMPORT/LOAD/RELEASE; synchronous wait in milliseconds, default 60000. |

Query consistency uses the connection property `consistencyLevel`, **not** `/*+ consistency_level=Strong */`. CREATE TABLE's `WITH (consistency_level='Strong')` is a separate supported collection-creation option. Use SELECT's trailing WITH for search parameters such as nprobe/ef; DDL WITH values and placeholder rules are detailed in the manual.

### Failures, Cancellation and Retries

maxRetry applies only to recognized transient write failures; permanent/unknown errors are not automatically retried. Backoff starts at 100ms and doubles up to 1000ms per wait, checking cancellation and timeout. Next-page reads, ordinary INSERT/UPSERT and Import creation do not automatically use this policy.

Paged DML errors retain the phase, page number, confirmed rows/pages, cause and suppressed failures. Successful pages cannot be rolled back; a failing page may also have partially taken effect.

`Statement.cancel()` cancels this Statement execution only, not other Statements on the connection. Timeout includes caller pauses while reading and is checked before and after page reads. Cancellation/close does not guarantee interruption of an in-flight SDK RPC; its returned page is discarded and the iterator released.

## Other Commands and JDBC Results {#4-other-commands-and-jdbc-results}

- SELECT, COUNT, SHOW: use `executeQuery` and consume a result set.
- INSERT/UPSERT, UPDATE/DELETE, DDL, GRANT/REVOKE, IMPORT without RETURNING, LOAD/RELEASE, FLUSH: use `executeUpdate` or `executeLargeUpdate`.
- Separate multiple SQL statements with semicolons and use `execute` + `getMoreResults`, not JDBC batch. See the [complete result loop](./commands.md#jdbc-results).
- The [syntax manual](./commands.md) documents exact database, collection, partition, index, permission, alias, import and progress syntax and result columns.

## Vectors, Array and Generated Keys {#typed-values}

Besides Milvus AutoID, entities can use dbVisitor's `@Column(keyType=KeyType.UUID32)` or `UUID36`: values are generated on the client and assigned to the entity before INSERT. For a primary key, also specify `primary=true`, define a VARCHAR primary key with sufficient capacity, and disable AutoID. List inserts can use this strategy too, but it is neither a server sequence nor JDBC Batch. UUID configuration does not replace the primary-key rules of an AutoID collection.

JSON entity fields can use `JsonTypeHandler`, with `@Column(specialJavaType=LinkedHashMap.class)`, `LinkedList.class`, or `HashSet.class` selecting the deserialization type. JSON and native Array are different field types: an integer array entity property can use `Integer[]` directly, with `ARRAY<INT32>(capacity)` in the collection schema.

JsonTypeHandler can also serialize nested Beans, Maps, or collections into VARCHAR. Read them using `JsonType.jsonMap()`, `JsonType.jsonList()`, `JsonType.jsonSet()`, or a Bean with a type-binding annotation. Positional parameters, named parameters, and NULL are supported, but JSON text stored in VARCHAR does not provide native JSON-field path filtering.

Annotation Mapper `@Insert` and XML `<insert>` can use `useGeneratedKeys=true` with `keyProperty="id"` to populate Milvus AutoID. Use Long for an Int64 key property; Map parameters must be writable. A lone Map argument can receive the key even if id was initially absent. Omit `keyColumn`: the common driver does not support `prepareStatement(sql, String[] columnNames)` and throws SQLFeatureNotSupportedException before writing. This does not affect RETURN_GENERATED_KEYS without column selection. Milvus has no relational sequence/last_insert_id; do not use selectKey to simulate them.

Field schema determines encoding; Java array shape alone does not. Mappings cover INSERT/UPSERT, UPDATE SET and corresponding KNN/range conditions.

| Milvus field | setObject input | getObject / JDBC read | Distance operators |
| --- | --- | --- | --- |
| FloatVector | Numeric List or six numeric primitive arrays | List&lt;Float> / getArray | `<->` L2, `<=>` COSINE, `<#>` IP |
| BinaryVector | byte[], ByteBuffer, byte List (-128…255) | byte[] / getBytes | `~=` HAMMING, `<%>` JACCARD |
| Int8Vector | byte[], ByteBuffer, numeric List, or any of the six numeric primitive array types; elements must be integers from -128 to 127 | byte[] / getBytes | `<->` L2, `<=>` COSINE, `<#>` IP |
| Float16Vector / BFloat16Vector | Numeric List/arrays or packed byte[]/ByteBuffer | Little-endian byte[] / getBytes | L2, COSINE, IP |
| SparseFloatVector | Nonempty Map&lt;Number,Number>, nonnegative integer indices and finite weights | SortedMap&lt;Long,Float> | `<#>` IP; `<?>` BM25 accepts text |
| Array | java.sql.Array, List, Java array | List / getArray with element JDBC type | Scalar filters |

ByteBuffer uses remaining bytes without changing its position. FP16/BF16 packed data uses two bytes per dimension; numeric inputs use SDK Float16Utils. Dimensions, finite values and metrics are checked. Array supports BOOL/integer/float/VARCHAR elements; boolean[] is a BOOL Array, whereas char[] is not a VARCHAR Array.

Declare Int8Vector as `INT8_VECTOR(dim)`, with one signed byte per dimension, unlike BinaryVector's bit vectors. Use HNSW indexes as required by the [official type documentation](https://milvus.io/docs/dense-vector.md), for example `CREATE INDEX idx_v ON items(v) USING HNSW WITH (metric_type=L2, M=8, efConstruction=200)`. The driver does not truncate fractions, accept unsigned values from 128 to 255, or automatically quantize floating-point vectors; inputs must match the model's quantization scheme.

To read an Array through dbVisitor, pass `Integer[].class`, `Float[].class` or `String[].class` to `JdbcTemplate.queryForObject`. Writes can use JDBC `createArrayOf`/`setArray`, or `new SqlArg(values, Types.ARRAY, new ArrayTypeHandler())`, including named parameters and UPDATE. Entity fields support default array mapping, `jdbcType=Types.ARRAY`, an explicit ArrayTypeHandler, and Number[] mapped through `specialJavaType=Integer[].class`; element types, max_capacity and nullable must still match the native collection schema.

JdbcTemplate.executeBatch is usable, but the common JdbcTemplate implementation executes statements individually for this driver. It does not call JDBC addBatch/executeBatch, provide batch atomicity, or imply high-throughput multi-row writes.

This path supports inserts, updates, and deletes with positional or named parameters. Milvus INSERT does not reject duplicate primary keys, so duplicate keys do not trigger batch failure as a relational unique constraint would. Use UPSERT explicitly when replacing data by primary key. The driver does not issue extra queries to check uniqueness or automatically rewrite INSERT as UPSERT.

Fragments assume Connection conn. Ordinary INSERT/UPSERT is not automatically retried. fetchSize=0 uses the SDK page default; larger values are capped at the SDK page maximum, without limiting total rows. VALUES ? accepts a lazy Iterator; caller-owned input resources are not closed by the driver.

```java
String create = "CREATE TABLE typed_demo (id INT64 PRIMARY KEY AUTO_ID, " +
        "tags ARRAY<VARCHAR(30)>(8) NULL, embedding FLOAT16_VECTOR(2))";
try (Statement stmt = conn.createStatement()) { stmt.executeUpdate(create); }
String insert = "INSERT INTO typed_demo (tags, embedding) VALUES ?";
List<Object[]> rows = Arrays.asList(
        new Object[] {new String[] {"java"}, new float[] {1, 2}},
        new Object[] {null, new float[] {3, 4}});
try (PreparedStatement ps = conn.prepareStatement(insert, Statement.RETURN_GENERATED_KEYS)) {
    ps.setFetchSize(256);
    ps.setObject(1, rows.iterator());
    System.out.println(ps.executeLargeUpdate());
    try (ResultSet keys = ps.getGeneratedKeys()) {
        while (keys.next()) {
            System.out.println(keys.getObject("id"));
        }
    }
}
```

Keys are SDK-returned Int64/VarChar IDs, including explicit keys and AutoID; ordinary UPSERT also trusts returned IDs. maxRows does not truncate keys. Unrequested keys are not accumulated; requesting every key requires O(number of keys) memory. Failures report phase, confirmedPages, confirmedRows and currentPageRows. Confirmed pages are not rolled back, and failed writes may have taken effect: do not blindly replay them.

## Hybrid, BM25 and Import {#6-hybrid-bm25-and-import}

This SQL creates BM25 schema/indexes and fuses two single-query searches on the server. Candidate LIMITs control each ANN request; outer LIMIT/OFFSET applies to one fused ResultSet, not multiple query-vector groups or JDBC batch.

```sql
CREATE TABLE search_demo (
    id INT64 PRIMARY KEY,
    body VARCHAR(2000) WITH (enable_analyzer=true),
    dense FLOAT_VECTOR(2), sparse SPARSE_FLOAT_VECTOR,
    FUNCTION bm25_fn USING BM25 (body) INTO (sparse)
);
CREATE INDEX dense_idx ON search_demo(dense) USING FLAT WITH (metric_type=L2);
CREATE INDEX sparse_idx ON search_demo(sparse) USING SPARSE_INVERTED_INDEX
    WITH (metric_type=BM25, bm25_k1=1.2, bm25_b=0.75);
LOAD TABLE search_demo;
INSERT INTO search_demo (id,body,dense) VALUES (1,'vector search',[1,2]);
SELECT id,score FROM search_demo ORDER BY HYBRID (
    dense <-> [1,2] LIMIT 20,
    sparse <?> 'vector search' LIMIT 20
) LIMIT 5 WITH (reranker='rrf',k=60);
```

Alternatively use WITH (reranker='weighted',weights='[0.7,0.3]'), one finite [0,1] weight per candidate. Ordinary ORDER BY still accepts one vector. Ordinary Hybrid has no native iterator and requires explicit LIMIT; [grouped search](./commands.md#grouping) instead requires explicit group_limit, while SQL LIMIT continues to count rows. Server search-window limits still apply, and fetchSize does not paginate server fusion. Milvus computes function outputs; omit them in writes. See the manual for TextEmbedding provider/model parameters and server configuration.

Import neither loads data files into Java memory nor uploads local files. Prepare/upload JSON/Parquet/NumPy using official BulkWriter or other tools, then submit and inspect using JDBC:

```java
String submitSql = "/*+ sync=false */ IMPORT FROM ? INTO search_demo " +
        "WITH (timeout='2h') RETURNING JOB_ID";
String jobId;
try (PreparedStatement ps = conn.prepareStatement(submitSql)) {
    ps.setObject(1, Arrays.asList(Collections.singletonList("prepared/a.parquet"),
            Collections.singletonList("prepared/b.parquet")));
    try (ResultSet rs = ps.executeQuery()) { rs.next(); jobId = rs.getString("JOB_ID"); }
}
try (PreparedStatement ps = conn.prepareStatement("SHOW IMPORT ?")) {
    ps.setString(1, jobId);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            System.out.println(rs.getString("STATE") + " " + rs.getString("REASON"));
        }
    }
}
```

SHOW IMPORT/SHOW IMPORTS returns JOB_ID, STATE, PROGRESS, TOTAL_ROWS, IMPORTED_ROWS, REASON and DETAILS (raw JSON including per-file details). Missing progress is SQL NULL, not zero. List jobs with SHOW IMPORTS FROM search_demo WITH (page_size=20,current_page=1); pagination support depends on the target REST version. Default IMPORT waits synchronously: hint timeout=60000 is the client wait in milliseconds, whereas WITH timeout='2h' is a server job deadline. Timeout/cancellation does not cancel the server job. Waiting failures retain the known Job ID and last progress without resubmitting. If the create response itself is lost, the ID may be unknown: reconcile through the job list.

`IMPORT ... RETURNING JOB_ID` returns a result set; use `executeQuery`. See the [support matrix](./compatibility.md#boundaries) for SQL and non-transactional boundaries.

## Consistency and Execution Controls {#execution-controls}

SDK 2.6.22's `QueryIterator` forces collection-default consistency when sending requests. Consequently, paged SELECT and DML row selection through this path cannot rely solely on the connection setting `consistencyLevel=Strong` for immediate read-after-write visibility. If you need this behavior, create the collection with `WITH (consistency_level=Strong)`. The driver does not implicitly change collection consistency settings.

Distinguish these controls:

- `connectTimeout` / `rpcDeadline`: connection or per-RPC timeout, in milliseconds.
- `Statement.setQueryTimeout(seconds)`: this execution's time budget, including retries and later ResultSet page reads, in seconds.
- SQL hint `timeout`: synchronous IMPORT/LOAD/RELEASE wait, in milliseconds, default 60000. It is not a universal timeout for every command.
- `Statement.setFetchSize(rows)`: page size set before execution, not a JDBC URL property or a total row limit.
