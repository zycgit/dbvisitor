# 1. Introduction

{/* llms:start */}

**dbVisitor is a unified data access foundation built on the JDBC standard. Its guiding idea is One Access, expressed in the vision "One APIs Access Any DataBase".** It serves storage and retrieval scenarios involving structured, semi-structured and unstructured data, giving Java applications a shared API or consistent programming style across relational, document, key-value, search and vector databases.

For example, one application can keep business records in MySQL, documents in MongoDB and cached values in Redis, search content with Elasticsearch and retrieve similar vectors with Milvus while reusing parameter binding, result mapping, Mappers and connection access patterns. One Access aims to reduce the learning and maintenance cost of different data source categories and let new sources fit existing data access patterns.

## Two-layer adapter architecture

| Layer | Responsibility | Implementation |
| --- | --- | --- |
| Application adapter: how to operate on data | Unify the API used by business code and manage query syntax and mapping differences | `LambdaTemplate` and `BaseMapper` generate SQL or target commands through dialects; Mapper annotations and XML organize SQL/DSL; `JdbcTemplate` executes SQL, DSL or native commands supported by the driver |
| Protocol adapter: how to connect | Expose data source protocols through JDBC connections, statements, parameters and results | Relational databases use vendor JDBC drivers; `jdbc-mongo`, `jdbc-elastic`, `jdbc-redis` and `jdbc-milvus` adapt their respective SDKs/protocols into JDBC drivers |

JDBC connects the layers: business code uses an application API, that API calls a JDBC driver, and the driver accesses the target data source. The application APIs share underlying mechanisms, while the drivers can also serve other JDBC tools independently. Projects can adopt the complete data access stack or introduce a driver adapter into an existing stack.

To integrate a new data source, implement a [custom JDBC adapter](../drivers/dev/about.md) using `dbvisitor-driver` and reuse the application access patterns. Add a matching database dialect when builder support is needed.

## Data models and use cases

| Data model or use case | Representative data source | Driver and capability reference |
| --- | --- | --- |
| Structured records and relational queries | MySQL, PostgreSQL, Oracle and others | Vendor JDBC drivers; [capabilities by data source](../features/overview.md) |
| Documents and semi-structured data | MongoDB | `jdbc-mongo`; [document operations and mapping](../features/mongo/about.md) |
| Key-value data, caching and data structures | Redis | `jdbc-redis`; [command access and result mapping](../features/redis/about.md) |
| Content search and unstructured text retrieval | Elasticsearch | `jdbc-elastic`; [search, Query DSL and index operations](../features/elastic/about.md) |
| Vectors and similarity search | Milvus | `jdbc-milvus`; [collections, scalar filters and vector operations](../features/milvus/about.md) |

One Access recognizes and manages differences: it unifies calling patterns, parameter binding and result handling while preserving native data source capabilities. Consult [data source differences](../features/overview.md) for supported commands, builders, transactions, batches and pagination. For example, Redis uses `JdbcTemplate` or Mappers for commands and currently has no builder dialect.

## Choose an API by task

| Requirement | Entry point | Read next |
| --- | --- | --- |
| Execute existing SQL, DSL or native commands with parameters and mapped results | `JdbcTemplate`; use `queryForList` or `queryForObject` for queries and `executeUpdate` for changes | [Programmatic API](./api/jdbc.md) |
| Reuse condition builders and CRUD patterns across supported data sources | `LambdaTemplate` or `BaseMapper`; the matching dialect generates SQL or target commands | [Builder API](./api/lambda.md) |
| Organize DAOs as Java interfaces and manage SQL/DSL together | `Session.createMapper(...)`; combine method annotations, `BaseMapper` CRUD and XML | [Mapper API](./api/mapper.md) |
| Use Map values as the data carrier | Distinguish Map mode with entity mappings from Freedom mode with table and column names | [Map queries](./core/map_query/about.md) |
| Query vector similarity | Choose KNN ordering or range filtering supported by the data source dialect | [Vector queries](./core/vector_query/about.md) |

`Configuration` creates a `Session`, which creates Mapper interface instances. Templates, Mappers and builders can be combined within one application; choose a shared builder or native commands according to the target data source capabilities.

## Choose dependencies and runtime

To use both layers, add `net.hasor:dbvisitor` and the target JDBC driver: a vendor driver for a relational database or a matching `jdbc-*` adapter for NoSQL or vector databases. To keep an existing access stack such as Spring JDBC or MyBatis, use a [driver adapter](../drivers/about) independently, following its supported commands and JDBC capabilities.

dbVisitor embeds directly in ordinary Java applications and provides framework integrations: `dbvisitor-spring-starter` for Spring Boot, `dbvisitor-spring` for ordinary Spring, `dbvisitor-hasor` for Hasor, `dbvisitor-solon-plugin` for Solon, or `dbvisitor-guice` for Guice. All these published modules use groupId `net.hasor`.

## Complete a first call

1. Identify the data model and target data source, choose the driver and runtime dependencies, and prepare a `DataSource` or `Connection` plus target resources such as tables, collections or indexes.
2. Where the dialect supports it, use `new LambdaTemplate(dataSource)` to reuse condition builders. For existing SQL/DSL or commands, use `new JdbcTemplate(dataSource)`. For Mapper interfaces, obtain a Session through `new Configuration().newSession(dataSource)`.
3. Select an overload for a single row, multiple rows, a scalar or a Map. Bind input values and handle results and exceptions.
4. Establish connection and transaction ownership. Standalone applications close their resources; framework applications use integration-managed objects and transactions instead of creating a separate connection environment.

Start with [ordinary Java](./yourproject/with_java.mdx), or follow the matching [Spring](./yourproject/with_spring.mdx), [Hasor](./yourproject/with_hasor.mdx), [Solon](./yourproject/with_solon.mdx) or [Guice](./yourproject/with_guice.mdx) integration guide.

## Why use it?

In the past, when relational databases were dominant, data access methods had become diverse and a large number of mature JDBC-based tools emerged.
However, with the rise of NoSQL databases, data storage forms became more diverse and access APIs became more complex.
Developers need to switch between different APIs, increasing learning costs and usage difficulty.

Existing data access technologies such as Hibernate, MyBatis, Spring JDBC, etc., mainly target relational databases and show limitations when facing increasingly diverse non-relational storage.

The core breakthrough of dbVisitor lies in the seamless integration of access modes: developers can mix multiple access paradigms in the same project and obtain a unified experience between relational and non-relational storage.

In terms of API design, dbVisitor provides APIs with a style similar to Spring JdbcTemplate, MyBatis. This design allows developers to avoid accepting a large number of new concepts and knowledge, thereby reducing learning costs and usage difficulty.

## Getting Started

- dbVisitor uses the [Programmatic API](./api/jdbc) to execute SQL, DSL or native commands supported by the target driver.
- dbVisitor supports accessing the database using the [Declarative API](./api/mapper) by marking interfaces with annotations.
- dbVisitor uses the same [Builder API](./api/lambda) across data sources with the required dialect capabilities.
- dbVisitor supports [Map Query Mode](./core/map_query/about) for Map-based data, either reusing object mapping or using table and column names directly.
- dbVisitor supports [Vector Query](./core/vector_query/about) for KNN ordering and vector range filtering.
- dbVisitor supports organizing DAOs as Java interfaces through the [Mapper API](./api/mapper), including annotations, BaseMapper CRUD methods, and Mapper files.
- dbVisitor supports unified management of SQL statements using [Mapper XML](./api/file_mapper) files.
- dbVisitor provides multiple ways to handle [Arguments](./args/about), believing that a suitable way can always be found to handle them in various special scenarios.
- dbVisitor provides a more flexible and efficient [Rule](./rules/about) mechanism, which makes maintaining application SQL more concise.
- dbVisitor has built-in multiple [Type Handlers](./types/about), which can conveniently handle most database types.
- dbVisitor supports using [Transactions](./transaction/about) between multiple different method calls.
- dbVisitor provides shared APIs or consistent programming patterns for [Redis](../features/redis/about), [MongoDB](../features/mongo/about), [Elasticsearch](../features/elastic/about) and [Milvus](../features/milvus/about).

## Integration

- [dbvisitor-spring](./yourproject/with_spring): Supports automatic configuration and injection of dbVisitor configured Mappers and instances in [Spring 4.x](https://spring.io/projects/spring-framework) and [Spring Boot 2, Spring Boot 3](https://spring.io/projects/spring-boot).
- [dbvisitor-solon](./yourproject/with_solon): Supports automatic configuration and injection of dbVisitor configured Mappers and instances in applications using [Solon](https://solon.noear.org/) as the application development framework.
- [dbvisitor-hasor](./yourproject/with_hasor): Supports automatic configuration and injection of dbVisitor configured Mappers and instances in applications using [Hasor](https://www.hasor.net/) as the application development framework.
- [dbvisitor-guice](./yourproject/with_guice): Supports automatic configuration and injection of dbVisitor configured Mappers and instances in applications using [Google Guice](https://github.com/google/guice) dependency injection.
- [jdbc-redis](../drivers/redis/about): A JDBC driver adapter for Redis, allowing developers to operate the database using standard JDBC interfaces and Redis commands.
- [jdbc-mongo](../drivers/mongo/about): A JDBC driver adapter for MongoDB, allowing developers to operate the database using standard JDBC interfaces and MongoDB commands.
- [jdbc-elastic](../drivers/elastic/about): A JDBC driver adapter for ElasticSearch, allowing developers to operate the database using standard JDBC interfaces and ElasticSearch QueryDSL.
