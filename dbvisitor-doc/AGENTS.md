# 文档工程 AI 编辑约定

本文件适用于 `dbvisitor-doc/`。以下标题规范针对中文博客 `blog/` 和英文博客 `i18n/en/docusaurus-plugin-content-blog/` 中的文章，不直接套用于 API 手册、版本说明或代码标识符。

新增、翻译或整理博客前，先阅读本文件及 [README](./README.md) 中的博客维护说明。AI 生成的第一版也必须遵守这些约定，不要留到发布时才压缩标题。

## 标题长度

| 标题类型 | 建议长度 | 上限 |
| --- | --- | --- |
| 中文文章大标题（front matter `title`） | 12–24 字符 | 28 字符 |
| 英文文章大标题（front matter `title`） | 24–42 字符 | 45 字符 |
| 中文小标题（正文各级章节标题） | 4–12 字符 | 20 字符 |
| 英文小标题（正文各级章节标题） | 8–22 字符 | 26 字符 |

计数规则：

- 按最终可见文字的 Unicode 字符数计算，不按字节数或英文单词数计算。可用 JavaScript 的 `Array.from(text).length` 核对纯文本标题。
- 汉字、英文字母、数字、空格、标点均各计 1 个字符；中文标题内的英文术语也逐字符计数。
- 可见的章节编号（如 `2.1 `）计入长度；Markdown 标记、链接地址、YAML 引号和显式锚点 `{#id}` 不计入。
- `##` 等 ATX 标题和下划线形式的 Setext 标题均适用；代码块内的 `#` 注释不是标题。
- 建议长度不是最低字数，不为凑长度添加修饰词。上限不是要写满的目标。

## 标题措辞

- 准确表达文章或章节实际提供的内容。介绍处理方案，就让读者看到“映射”“处理”“写入”等主题；不要只用悬念式问题吸引点击。
- 大标题保留核心技术对象与主要用途，不堆叠版本号、框架名、API 全名和多个副标题。
- 小标题用于目录定位，优先采用短的主题词或动作短语。删除重复的“先……再……”“如何……才……”，不要把段落结论整句搬进目录。
- API 全名、参数清单、补充解释放在正文中；不能为了长度擅自缩写技术名称、改变含义或使用含糊标题。
- 中英文表达同一含义，但分别组织措辞，不逐字翻译。允许英文省去中文标题中重复的上下文。
- 无法在上限内准确表达时，先重新组织标题；仍需超限则明确向用户说明原因，不默默放宽限制。

示例：

| 避免 | 推荐 |
| --- | --- |
| 公元前日期，为什么会差一年？（正文重点是处理方案） | 公元前日期映射：两种处理方案 |
| 记录流：不用先收集成一个大 List | 迭代器写入 |
| 失败后，先弄清楚哪部分已经完成 | 失败处理 |
| Milvus Ingestion: Three Approaches and When to Use Them | Milvus Ingestion: Choosing a Write Method |
| Streams: no need to collect everything into a List | Iterator Writes |

## 修改边界与检查

- 整理标题不授权改写正文、代码、配图、章节层级或文章 `slug`；不要顺手扩展修改范围。
- 修改既有小标题时保留原锚点，例如 `## 迭代器写入 {#原锚点}`，保证已有章节链接可用。修改大标题也不改变文章地址。
- 纯标题整理不修改原始发布日期，也不自动刷新 `last_update`；实质性内容修订按 README 的更新时间约定处理。
- 交付前核对中英文长度、标题与内容的一致性，以及章节锚点。两种语言均需检查，不能只压缩中文。
- 长度只是约束，不保证任意字体和屏宽下都不换行。大标题还需看“全部”列表，小标题需看文章右侧目录；以 1440px 桌面视口作基本检查，窄屏允许自然换行。
- 不通过缩小字号、扩大侧栏、隐藏溢出或省略号来掩盖冗长标题。修改博客后执行 `npm run build` 验证中英文站点；无法构建或预览时，如实说明未验证的部分。
